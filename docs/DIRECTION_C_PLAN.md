상태: **계획 초안, 팀 합의 전** (2026-10-02). 현재 파이프라인(검색 + 원문 근거 답변, 논문 초안의 RAG·RAGAS 평가)을 뼈대로 두고,
교수님 가이드(PDF v1.2)의 뒷단계를 단계별로 **추가**한다. 기존 파일은 최소한으로만 고친다.
관련 문서: `docs/function_contracts.md` 12~17장, `docs/eligibility_design_draft.md`, `docs/HANDOFF.md`, `docs/HANDOFF_NEXT.md`.

## 2. 단계 1의 합의 항목 (`eligibility_design_draft.md` 7절 요약)

1. `employment_status` 등 값 형식: 코드값(`employed`) vs 한글 라벨(`미취업`) — 가장 먼저
2. 소득 표현: 1차는 "기준중위소득 %"로 표기된 조건만 자동 판정할지
3. OR 조건·우대 조건: 1차는 `other`로 두고 자동 판정 제외할지
4. 민감 항목(소득·장애·수급) 질문 시점과 안내 문구, 저장 안 함(세션 메모리만)
5. API 형태: 계약서 17장은 `/sessions/{id}/eligibility`, 현재 API는 상태 없는 방식이라 `/policies/{id}/eligibility` 후보
6. 추출 결과 캐시 위치와 무효화 방법
7. 정답 세트를 만들지 여부

## 3. PDF와 설계 초안의 차이 (결정 필요)

- PDF 16쪽은 LLM이 만든 조건 데이터를 **담당자가 확인**한다고 한다. 현재 설계 초안에는 이 확인 절차가 없다(후처리 검증만 있음).
  → 정답 세트 작성 시 담당자 확인 절차를 같이 둘지 결정.
- PDF 25쪽은 잘못 검색된 문단(다른 제도·옛 기준)을 버리고 재검색한다. 현재는 없다(단계 4에서 다룸).
- PDF의 금액·기준값(1,230,834원 등)은 **교육용 예시**다. 코드에 직접 넣지 말고 고시를 확인해 버전 관리한다.

## 4. 위험 (확인 필요)

- 신청서 초안(단계 3)은 정책별 신청서 **칸 구조**를 알아야 한다. 현재 DB에서 확인된 것은 서식 파일 URL뿐일 수 있다.
  → 칸 구조가 없으면 "공통 항목 메모(지역·가구원·소득 등)" 수준으로 범위를 줄인다. 단계 3 시작 전에 데이터 확인 필요.
- LLM 추출 오류가 `not_eligible`로 이어지면 신청 기회를 잃는다. 수치 불일치가 명확할 때만 `not_eligible`, 애매하면 `unknown`.
- 민감정보(소득·장애)와 계좌번호·연락처는 서버에 저장·로그하지 않는다.
